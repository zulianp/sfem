SFEM Codegen Architecture

The layer graph is now clean and enforced. The layers themselves are not yet doing the jobs they are named for — one of them holds 22,970 lines that should be a printer.

Package python/codegen/framework Branch codegen-layering, 20 commits from 060684ff Out of scope the mlir/ subtree Date 2026-09-02

This document separates two things that the previous analysis deliberately ran together: what the architecture requires of each layer, and what each layer currently is. They are drawn against the same eight rows so the difference can be pointed at rather than described. Everything after that is the list of decisions still open, with the cost of each and what it blocks.

Where things stand

Structure is done: every import in the framework points up the lowering order, zero violations, enforced by a test that fails on any new one. The specification layer has no outgoing edges at all. The planning layer exists. Nothing architectural lives outside the framework.

Behaviour is not. The emission layer still makes the decisions the planning layer is supposed to make — which loops exist, what hoists to which scope, which buffers are gathered, how a matrix scatters. Thirteen plan types and six assembly plans describe those decisions and no emitter reads any of them.

Put plainly: the boxes are in the right places and the arrows point the right way, but the work is still being done in the wrong box. Every open point in Part 3 is either that problem or a consequence of it.

PART 1 · PRESCRIPTIVE

What each layer must own

Eight layers. Each boundary is placed where a distinct kind of decision is finished, and the test of a boundary is that a concept is nameable above it and unnameable below it. The figure pairs each layer's requirement with what occupies it today, so the two readings share a row.

The rules that make a boundary real

Three, each enforced by a test rather than asserted in prose. They are what stopped the layer graph regressing while 6,000 lines moved between packages.

PART 2 · DESCRIPTIVE

What is actually built

Two facts about the current tree. The first is good and finished; the second is the reason this document exists.

The import graph is clean

Twelve layer-to-layer edges, every one pointing up the lowering order. It started at seventeen edges with six pointing the wrong way, including all four leaving the specification layer.

The decisions are still in the wrong layer

What the clean graph does not show: the emission layer receives plan objects and ignores them, re-deriving the same decisions internally from SymPy and element metadata. The plan layer describes the kernel; the emitter builds a different description of the same kernel in control flow and strings.

PART 3

Open points

Nine, ordered by what unblocks what. One is closed and one is under way since this document was written. The rail colour is status: blocked waits on something above it, needs a decision is yours to call, ready can start now.

OP 0
The matrix-free apply matrix stated and verified; 1 of 4 axes drives

The matrix-free action is the framework's primary product — 219 of the 520 generated files — and every kernel is emitted several times over across four axes: mesh traversal, geometry mode, element data layout, and precision. Which combinations exist was written down nowhere; it was readable only by generating the output and looking at what came out.

plans/apply_variants.py now states the rule, verified against the real tree: 181 of 181 apply kernels predicted exactly across all eleven materials. The rule has genuine content — AoS only ever appears with isoparametric geometry, and never for Taylor–Hood formulations, which is why poro-hyperelasticity and Stokes have no AoS variants at all; packed traversal applies to the Jacobian action only, never the residual; and packed isoparametric variants are skipped for TRI3 and TET4, whose isoparametric geometry is affine.

The precision axis drives. It was a literal tuple repeated seventeen times in one emitter; all seventeen now read the plan, and a test proves the difference between consulted and ignored by changing the plan and requiring the kernels to follow — drop a precision and its kernels vanish, add a third and a third full set appears. That is the precondition for the per-thread, per-warp and CUDA/HIP apply variants goal 8 asks for: adding a row is now a plan change.

The other three axes are still decided by the emitters. Precision was the one already expressed as a clean iteration; traversal, geometry and layout are branches woven through emission, and moving them is the harder half.

OP 1
Move the emitters' decisions into L3 under way — dependency analysis done

The root open point. residual_codegen.py (10,074 lines) and energy_codegen.py (8,483) decide loop structure, scope placement, stream layout, gather and scatter shape and geometry policy while building strings. The plan types for all of it already exist and are unread.

Done: the analysis family. plans/streams.py owns which field stream groups a kernel needs — the emitter keeps only how each is spelled in C. plans/dependencies.py owns dependency pruning: which roles are touched, which parameters survive, which coefficient entries are structurally zero. plans/boundary_usage.py owns whether a boundary form's coefficients reach for coordinates or current values, a question the emitter had been asking four times in two different shapes.

Done: the layout family. plans/layout.py takes 17 more functions — which shape function maps to which stream, where a field's components sit in a packed lane buffer, how tensor-product elements reorder into Cartesian order, and the mixed-order variants for Taylor–Hood. These decide the memory access pattern of every generated loop, and so whether the loads are unit stride.

Measured effect: the largest emitter contains zero free-symbol analysis, down from six references, and its text-free helper count has fallen from 32 to 18. residual_codegen.py is 9,875 lines, from 10,074. The boundary emitter is down from eight symbol scans to two, both argument validation rather than planning.

Done: kernel file naming. Which files a kernel produces and what they are called — LocalKernelPlan.name/.header and MeshKernelPlan.name/.source were already the definition, and the emitters rebuilt both from format strings. The idempotence rule the emitter carried privately (a prefix already naming its element does not get a second one) moved into the plan factory with it. This is the first move that changes the plan-consumption count: 13 unread, now 11.

Remaining: the rest of the structural family — loop nest and bounds, scope hoisting, gather and scatter shape, and geometry mode. These are the genuinely hard ones: unlike everything moved so far, they are not code that lifts out whole but structure that exists only as the shape of the emitter's control flow. The mesh phases, for instance, are spread across six large emission functions, each interleaving gather and scatter with buffer declarations that depend on the dependency set. They are what OP 2 and OP 4 wait on.

OP 2
Delete _target() blocked by OP 1

emitters/residual_codegen.py:74 is still def _target(): return OpenMPTarget(), with a twin in the boundary emitter — 14 call sites through eight zero-argument wrappers. It is no longer a layering violation, since an emitter may name a target, but it is what keeps a CUDA residual kernel a fork rather than an argument.

Threading a target parameter reaches 43 functions transitively, every one of them emitter internals that OP 1 is meant to collapse into a printer. Doing it first is work OP 1 undoes. Deferred deliberately, not overlooked.

OP 3
Make the six assembly plans drive assembly 1 of 6 done

CRSAssemblyPlan, BSRAssemblyPlan, DIAAssemblyPlan, COOAssemblyPlan, PatchAssemblyPlan and BlockDiagSymAssemblyPlan describe row pointers, column indices, block layout and accumulation policy. They were referenced in exactly three places: their definition, the facade re-export, and their own test.

CRS is converted. _scalar_crs_matrix_scatter_lines takes the plan and spells what it defines; the plan's defaults are the names the kernels have always used, so the text is unchanged, but changing the plan now changes the kernel. The reduction policy goes through a helper that raises on a policy it cannot spell rather than silently emitting a plain add. The other five have the same shape.

The two-stage approach holds: consume the plans at byte-identical output first, which proves they describe what is actually emitted, and only then change what they say — which is where OP 6 becomes the blocker.

OP 4
Route the residual path through KernelAST blocked by OP 1

ir/kernel_ast.py is a complete, well-formed kernel IR: typed loops with vectorization and tabulation strategies, buffers, gather and scatter nodes, geometry nodes, plus KernelASTPass and KernelASTPassPipeline. The residual path builds zero nodes; the energy path uses four fragments; the pass pipeline is referenced only from tests.

Every optimization the PRD asks for — vectorization, unrolling, blocking, scratchpad packing, per-warp variants — is a pass over this IR. There is nowhere else for them to live, and today nothing to attach them to.

OP 5
Enforce the one-dispatch-axis rule needs a decision

Two of the three architectural rules are enforced by tests. The third is not: nothing currently fails when a backend branches on unit.kind or a printer on if "crs" in formats. Both still happen.

A static check is feasible — flag string comparisons against a known vocabulary of upper-layer concepts inside lower-layer modules — but it will be noisy until OP 1 and OP 3 remove the real cases. The decision is whether to write it now as a failing ratchet with an allowlist, exactly as the layering test was written before the code moved, or wait.

OP 6
There is no performance gate needs a decision

Every step so far has been verified by byte-identical generated output across 11 materials — a stronger claim than a passing test suite, and one that settles performance by construction: identical emitted source compiles to identical kernels.

That gate stops applying the moment output changes on purpose, which is exactly what OP 3 stage 2 and most kernel-level optimization do. What replaces it is numerical parity plus throughput measured before and after, and that needs a compiled SFEM build and a benchmark harness. This worktree has neither. Nothing beyond the byte-identity frontier can be honestly verified until it exists.

OP 7

The suite has run at 10 failures and 13 errors throughout, an identical set at every step, and identical to the same suite on nonlinearspmg. They predate this work entirely. That made them a usable baseline, but "unchanged" is a weaker guarantee than "passing", and a genuine regression hiding inside a known-failing test would not be visible.

Two tidy-ups the layering test cannot see.
