SFEM Codegen Architecture

The layer graph is clean and enforced, and the matrix-free apply path is now measured as well as described. The emission layer still holds 23,409 lines that should be a printer — up from 22,727, because node construction is longer than string appends, which is why it is now measured by the decisions it makes rather than by its size.

Package python/codegen/framework Branch codegen-layering, 42 commits from 060684ff Out of scope the mlir/ subtree Date 2026-09-03 (second pass)

This document separates two things that the previous analysis deliberately ran together: what the architecture requires of each layer, and what each layer currently is. They are drawn against the same eight rows so the difference can be pointed at rather than described. Everything after that is the list of decisions still open, with the cost of each and what it blocks.

Where things stand

Structure is done: every import in the framework points up the lowering order, zero violations, enforced by a test that fails on any new one. The specification layer has no outgoing edges at all. The planning layer exists. Nothing architectural lives outside the framework.

Behaviour is not. The emission layer still makes the decisions the planning layer is supposed to make — which loops exist, what hoists to which scope, which buffers are gathered, how a matrix scatters. Thirteen plan types and six assembly plans describe those decisions and no emitter reads any of them.

Put plainly: the boxes are in the right places and the arrows point the right way, but the work is still being done in the wrong box. Every open point in Part 3 is either that problem or a consequence of it.

PART 1 · PRESCRIPTIVE

What each layer must own

Eight layers. Each boundary is placed where a distinct kind of decision is finished, and the test of a boundary is that a concept is nameable above it and unnameable below it. The figure pairs each layer's requirement with what occupies it today, so the two readings share a row.

The rules that make a boundary real

Three, each enforced by a test rather than asserted in prose. They are what stopped the layer graph regressing while 6,000 lines moved between packages.

PART 2 · DESCRIPTIVE

What is actually built

Two facts about the current tree. The first is good and finished; the second is the reason this document exists.

The import graph is clean

Twelve layer-to-layer edges, every one pointing up the lowering order. It started at seventeen edges with six pointing the wrong way, including all four leaving the specification layer.

The decisions are still in the wrong layer

What the clean graph does not show: the emission layer receives plan objects and ignores them, re-deriving the same decisions internally from SymPy and element metadata. The plan layer describes the kernel; the emitter builds a different description of the same kernel in control flow and strings.

Where it stands after the IR work

The shape is right; the direction of data flow is not. L3 computes the structure, L4 can now represent it, L6 prints it — and L6 still originates it. That is the same defect found and fixed twice in narrow places this session: the scheduler computed hoist_scope and the emitters re-derived the loop nest by hand; the driver selected a target and the emitters constructed their own. Both are closed. The general case is not.

Converting strings to nodes was a prerequisite for plan-driven emission, not a substitute for it, which is why the unread-plans measure correctly refused to move all the way through this work.

PART 3

Open points

Twenty, ordered by what unblocks what. Two are closed and one is under way since this document was written. The rail colour is status: blocked waits on something above it, needs a decision is yours to call, ready can start now.

OP 20
Energy and residual must lower to one form algebra phase 0 done — the evidence

The requirement. Both formulations lower to the same three objects — 0-form (energy, or a residual-based merit), 1-form (gradient, or the negated residual), 2-form (Hessian, or the Jacobian) — and nothing below the form layer distinguishes them.

The algebra already exists and stops at emission. symbolic/forms.py has FormOrder, StandardFormName, and FormCollection.form(order) / blocks_for(order). FormOrder is used 33 times in symbolic, 23 in plans, 18 in package, 20 in pipeline — and 0 times in emitters. The split below the form layer is not a flag the emitters test; it is the module boundary itself.

emitterlinesfunctionsdecisions in emission
energy_codegen.py8,989149110
residual_codegen.py9,865145126

Only seven function names are shared between them, and stripping the formulation word from the names adds none. They are parallel implementations of the same concepts rather than copies, which is why every capability is built twice and can diverge — and between them they hold 231 of the 233 decisions left in emission. The fork is one branch, in pipeline/driver.py, choosing an energy or a residual codegen unit on FormKind.

Phase 0 measured which representation is actually load-bearing, and it is not the forms. The parallel residual state — residual_fields, residual_expressions, jacobian_action_blocks — has 49 consumers across eight files. The form-order accessors have 19 across five. So re-keying is not a rename: it is making the form blocks become the representation everything reads, in place of the one they read now.

And the mismatch is sharper than the code comment says. Probing every material at the form layer:

  • Residual formulations key blocks by assembled field while their lowered fields are per component. Stokes lowers 1-form blocks u, p against fields u0, u1, u2, p. That is the documented mismatch, and it is why the parallel state exists.
  • Energy formulations populate no block metadata at all. Linear elasticity and neohookean report empty blocks at every order, while their form expressions are present and non-trivial. So the energy path does not merely key blocks differently; it does not use them.

One correction to the plan this phase was written from. It said the residual 0-form does not exist, on the strength of FormMetadata(FormOrder.ZERO) being appended with no blocks. The metadata has no blocks, but the form does have an expression: laplace's 0-form is κ²(∇u·∇v)²/2, which is already the shape of a merit. What is missing is the block metadata and a consumer, not the mathematics — so phase 2 is smaller than planned. Worth noting that this expression is the square of the weak-form integrand, test function included, rather than of the assembled residual vector; whether that is the intended merit is a question for whoever specifies it.

What phase 0 leaves behind. tests/test_form_keying_baseline.py records, for every material and dimension, which orders exist, what each order's blocks are keyed by, and what the lowered fields are called. Phase 1 then arrives as a diff against that file rather than as an assertion that nothing broke. It deliberately does not assert that the 1-form is the derivative of the 0-form: on the residual path the 0-form is a merit and the 1-form is the negated residual, and the two are not related that way.

OP 19
The mesh geometry a kernel takes is now the plan's decision done — 239 → 233

Choosing the next step by measurement rather than by feel: of the 239 decisions left in emission, 231 are in the two big emitters, and they split cleanly by what they read. The residual emitter's 126 are dominated by dependencies (74), testing exactly the flags the plan layer already answers — current, direction, previous, uses_adjugate. The energy emitter's 110 are dominated by form (65), testing name and weak_form, for which no plan exists. So the residual side was ready and the energy side needs design first; this took the ready one.

Which geometry buffers cross a mesh kernel's boundary — the symmetric gradient metric, or the Jacobian adjugate and determinant — was spelled by hand at twenty-five sites in the residual emitter, four in the energy one, and once more in the wrapper, each with its own if chain over the same flags. plans/geometry_quantities.py now states it once, and both the signatures and the calls are spelled from it.

This is the decision that had already gone wrong. The wrapper's copy spelled the adjugate unconditionally, so laplace generated for TRI3 or TET4 alone handed five geometry arguments to a kernel taking three and would not compile — OP 16's third defect. Fixing that made the instance go away; this makes the class go away, and a test pins it in the shape OP 3 established: the names the plan produces must appear in the emitted kernel, and changing the plan must change what is emitted, because the weaker assertion alone passes for an emitter that consults nothing.

All 505 files byte-identical at every step, so nothing about the generated code moved — only where the decision lives. The wrapper also stops recomputing dim * (dim + 1) / 2 for itself and reads the plan's count, which is the arithmetic both sides previously agreed on only by coincidence.

OP 18
Low-order Laplacian and elasticity want CSE expanded, and one of them already has it — as frozen text analysed; the plan is the work

The requirement is that the simplest and most important kernels — Laplacian and linear elasticity on low-order elements — expand their common subexpressions rather than sharing them, so the emitted code is small and the register footprint minimal. A shared subexpression is a value live in a register from its definition to its last use; for a low-order element the expression it names is tiny and cheap to recompute, so naming it buys almost no arithmetic and lengthens live ranges across a loop the compiler is trying to vectorise. This is the register-pressure mechanism OP 15 measured, pointing the other way.

kernelscalar temporarieslines
laplace · TET43892,093
laplace · TRI32141,729

linear_elasticity · TET42847,322
linear_elasticity · TRI3965,681
linear_elasticity · HEX802,505
neohookean_ogden · TET4, for contrast1867,141

Read the last row against the first. The Laplacian on TET4 carries more than twice the temporaries of a hyperelastic material on the same element — 389 against 186 — which is the wrong way round for the simplest operator in the framework, and is the measurement that makes the case.

The low-order Laplacian already has the kernel this asks for. There is a fast path that computes a TET4 element with six temporaries and four outputs, and a TRI3 element with three, straight from the metric components:

const scalar_t x0 = fff0 + fff1 + fff2;
const scalar_t x3 = fff1 * u0;
const scalar_t e0 = u0 * x0 + u0 * x1 + u0 * x2 - u1 * x0 - u2 * x1 - u3 * x2;
const scalar_t e1 = -fff0 * u0 + fff0 * u1 + fff1 * u2 + fff2 * u3 - x3 - x4;

It is hand-written C, as literal strings inside the emitter — 28 such lines across emitters/ — selected by a six-condition structural test that is also in the emitter: cached affine metric, one field, one quadrature point, n_shape == dim + 1, no previous state, and a matching stream group. Every one of those conditions is a property of the lowered form, which is to say a planning decision sitting in emission; and the kernel it selects is not derived from the form at all, it is transcribed.

Linear elasticity gets none of it. The gate tests for a Laplacian-shaped form, so elasticity falls through to the general path and its 284 temporaries. The technique is frozen exactly where someone wrote it out, which is the cost of holding it as text rather than as a policy.

So the work is to make it a plan. Expansion becomes a per-kernel decision the plan layer states — the structural test moves there, where it belongs, and gains the element-order and material conditions elasticity needs. Emission then generates the expanded body from the symbolic expressions with sharing suppressed, rather than reproducing transcribed arithmetic. Two things fall out: the Laplacian path stops being frozen text and starts being derived from the form it claims to implement, and elasticity gets the same treatment without anyone hand-writing it.

This is measurable now, which it was not an hour ago. The reproducibility harness reaches TET4 and drives ten laplace kernels including the metric family, with a recorded baseline and throughput saturating by refine=24. Whether expansion pays, and where it stops paying as the element order rises, is a measurement rather than an argument — and OP 15 is the standing warning that the intuition can be wrong in either direction.

OP 17
The precision axis multiplies the ABI, and should be a parameter stage 1 built; stage 2 open

Every kernel that touches scalar data is emitted twice. precision_axis() returns (double, "") and (float, "_float"), and each emitter loops over it, so the generated tree carries a full second copy of every kernel that differs from the first in one line — using scalar_t = float; — and in the types of its field parameters. They are not two instantiations of a template; they are two written-out bodies.

All 434 _float symbols have a twin — none is orphaned — and the 256 that do not pair are the matrix-format metadata and diagnostics accessors, which carry no scalar buffers and correctly sit off the axis. So the factor of two holds exactly wherever scalar data crosses the boundary, and the overall figure is 1.63× only because a fifth of the surface is metadata.

The form to adopt is SFEM's own, not a new one. operators/tet4/cuda/cu_tet4_laplacian.cu already routes exactly this problem: one extern "C" symbol, scalar buffers declared void *, and a const enum smesh::PrimitiveType naming their type at run time. The body switches over SMESH_DEFAULT, SMESH_FLOAT32 and SMESH_FLOAT64, casts, and calls a template that holds the specialised code; anything else raises SFEM_ERROR. Two details are load-bearing and both are already settled by that code. One enum governs a group of buffers that share a type — the parameter is real_type_xy because it covers x and y together, not one enum per pointer. And geometry is not on the axis: fff crosses as void * but is cast unconditionally to a fixed cu_jacobian_t, because its precision is a build-time property.

That last point is already true of the generated kernels, which is what makes the change tractable: diffing a precision pair, the geom_t geometry parameters are identical in both, and only the field buffers and the material scalar differ. cu_linear_elasticity_apply settles the material scalar too — mu and lambda cross as const real_t, a build-time type, not as part of the runtime axis.

So the target signature is a mechanical rewrite of the pair, taking laplace_tri3_jacobian_action_affine_mesh_soa_aos as the worked case: geometry stays const geom_t *, kappa becomes const real_t, the two field pointers become const void * and void *, and one const enum smesh::PrimitiveType real_type is inserted ahead of them. The body that exists twice becomes one template <typename scalar_t> function, and the entry point becomes the switch that selects it.

Where the decision lives. precision_axis() stops being an axis that multiplies symbols and becomes the list of runtime cases the switch spells — the same plan, read by emission for a different purpose, which is the shape OP 0 established for this axis when it was made plan-driven. The wrapper loses an axis outright: package/op_wrappers.py currently selects a symbol by precision and would instead pass a value.

Two things this must not break, and one gate that does not yet exist. Byte-identity breaks by design here — this is precisely the case OP 14 built tools/reproducibility.py for, and the 148 kernel digests are the correctness statement that has to survive unchanged. The second is performance, and it is the real risk: the standing rule in this codebase is that nothing trades measured CPU throughput for cleanliness. Moving a kernel body behind a template and a runtime switch should be free — the switch runs once per call, outside the element loop, exactly where SFEM's CUDA operators put it — but "should be" is not a measurement, and inlining and vectorisation of these bodies are sensitive. A throughput gate before and after, on the same machine, is a precondition for this change rather than a follow-up to it.

The Op class mirrors GPULaplacian. It declares enum smesh::PrimitiveType real_type{smesh::SMESH_DEFAULT}; as a public member, carries it through clone(), and hands it to every kernel call alongside the buffers — whose interface types do not change, because the base Op methods take real_t * and a real_t * converts to void * at the call. That is exactly what gpu_laplacian_block_vector does. The generated Op has no clone() and keeps its state behind a pimpl, so the member is the one visible addition.

The work splits in two, and the half that was asked for is the safe half. Classifying every _float definition by whether its body actually contains a kernel — a loop, a #pragma, a using scalar_t — rather than by size:

Every one of the 434 public entry points is pure forwarding — an element-type switch, or a single return sfem::codegen::IMPL<scalar_t, geom_t>(…) over a template that already exists. So collapsing the entire public ABI compiles no kernel body differently from today: the same template instantiations are called, from one symbol instead of two. Throughput cannot move, and the factor of two lands in full. That is stage one, and it carries no performance risk to gate.

Stage two is the 478 definitions that do carry a body, holding 7.6 MB of the 8.7 MB. Those bodies open with using scalar_t = float; and are written out in full, so collapsing them means turning each into a template <typename scalar_t> and letting the compiler instantiate it. That is where the source saving is and where the inlining and vectorisation risk is, and it is the part the throughput gate exists for.

Stage one is built. The public ABI is 1,124 → 690, exactly the predicted 1.63× overall and 2× on every symbol that carries scalar data. All 291 translation units compile, all eleven materials. The 74 surviving kernel digests reproduce the recorded baseline exactly, and the gate reports the 74 that no longer generate — the _float twins — rather than passing silently over them. Throughput on the benchmarked laplace kernels is unchanged: six comparable kernels within ±1%, two of them bit-identical, against a ±2% noise floor. Generated source is 0.2 MB larger, which is the expected shape of this stage: it adds the switches without yet removing a single kernel body.

Three things had to be repaired along the way, and one of them was mine. The mixed-order materials pass a vector field as an array of pointers, and an array does not convert its element type implicitly the way a pointer does, so both the parameter and the argument need the cast spelled out. The reproducibility harness could not bind the new ABI at all — it matched concrete C types, and void matched none of them — so the correctness gate was briefly blind to the very change it existed to check; it now binds runtime-typed entry points at SMESH_FLOAT64, which is what makes the digests comparable with the baseline. And the gate had a second blindness that this branch introduced when kernel-to-material scoping was fixed earlier: scoping by what was measured this run made a kernel that stops generating invisible, so 74 could vanish with the gate still green. Baseline entries now carry their owning material.

Stage two: one of four sites, under a gate that had to be built first. Only four emission sites write a full kernel body — they are the ones emitting using scalar_t = … — and the body is otherwise the same text for every precision, so it lifts into a template <typename scalar_t> behind one runtime-typed entry point.

The first attempt was converted, compiled, and reverted, because checking the gates rather than assuming them showed that neither could see it. The converted site emits the simplex-metric _aos kernels; the harness drove a HEX8 grid, so zero of them were among the 74 digests, and the throughput readings taken beside them were noise from untouched kernels — the same kernel read +2.3% on one run and −4.9% on the next. A change to kernel bodies with correctness unproven and throughput unproven is the one thing this codebase does not accept on an argument.

Three things were missing from the gate, none of them emitter work. algebra/ was not on the harness include path, so tet4_inline_cpu.hpp could not find sortreduce.hpp and TET4 would not compile at all. --element did not exist, so a material could only be driven on its default grid. And the harness had no gradient metric to supply, which is exactly the geometry these kernels take — it now carries fff in both layouts, filled by calling SFEM's own tet4_fff rather than by reimplementing a convention that could drift from the kernels being checked. TET4 went from 4 driven kernels to 10, the six new ones being the family stage two rewrites.

With the gate in place the conversion holds. All 10 TET4 answers match the recorded baseline, affine/isoparametric parity holds, and the HEX8 gate still reports 74 of 74. Throughput at a saturating size, twice: every converted kernel within ±2% except one, and that one is +97% — laplace_residual_3d_affine_mesh_soa_aos goes from 23.30 to 45.9 MDOF/s. That reproduces: three samples of the old build read 23.30, 26.52 and 28.13, two of the new read 45.85 and 45.92. Instantiating the body as a template appears to optimise where the written-out one did not; the number was suspicious enough to re-measure the baseline before believing it.

Three sites remain, holding most of the 7.6 MB — this one is 0.1% of the tree. They are now ordinary work rather than blocked work.

Open, and worth deciding before building stage two. SMESH_DEFAULT maps to real_t, which in most builds is double, so mirroring SFEM gives three instantiations where there are two today — object size grows even as the ABI halves, unless DEFAULT is folded into the matching concrete case. And the material scalar moving to real_t is a small semantic change: a caller running in single precision currently hands these kernels a float parameter and would hand them a real_t.

OP 16
L7 reconstructs the kernel ABI instead of being handed it contained and gated; the layering cause is open

Two operators had never compiled. Stokes and poro-hyperelasticity emit wrappers that call their own kernels with the wrong number of arguments — two too many for Stokes on every residual and Jacobian action, six for poro. Not a subtle disagreement: candidate function not viable: requires 16 arguments, but 18 were provided, on eleven of the eleven materials’ worth of gates being green. The generated code for two materials could not be built at all, and the framework did not know.

What the disagreement is. A multi-component field crosses the wrapper/kernel boundary two different ways. Most kernels take one pointer per component, const double *const u0, const double *const u1. The mixed-order Taylor–Hood kernels take a single array-of-pointer, const double *const u_data[2], because the field’s components live on different spaces and plans/streams.py groups them into one stream bundle. The wrapper expanded component-wise, unconditionally.

materialarray-of-pointer paramsper-component params
poro_elasticity112450
stokes112210
the other nine materials01,876

Read that table before choosing a fix. The convention is not a property of the material — both mixed-order materials emit both forms — and not a property of the field, which is the same field either way. It is settled per kernel, by the layer that decides how streams are bundled. Any rule the wrapper can evaluate from what it holds is the wrong rule. The first attempt at this proved it: inverting the expansion made Stokes and poro compile and broke the nine materials that use the other form, with Kelvin–Voigt failing in exactly the mirrored way.

The cause is that L7’s only channel to the rest of the framework is generated C++ text. package/op_wrappers.py is 7,610 lines and 141 functions, a third of it literal C++ in 33 template strings, and its complete import list is json, os, re. It reads no plan, no IR, no target description. What it reads instead is the output of the layer above it: _extract_c_abi_declarations scans the emitted sources for extern "C", finds the brace or semicolon that ends each one, and lifts the declarations out — and that scrape is what becomes the public header of every generated operator. Eight functions and 443 lines do this, across twenty regex and scan operations.

So the packaging layer is a C++ parser sitting immediately downstream of a C++ printer, with a text format between them that no layer owns. Everything it needs to know about the code it calls — kernel names, argument order, argument shape — either survives that round trip or is re-derived in parallel with the emitters, which by contrast reach into plans twenty-two times in the residual emitter and five in the energy one. The call shape is one of the things that does not survive: a signature knows whether a parameter is u_data[3] or u0, u1, and the wrapper’s own reconstruction of the field list does not.

This also settles what the containment is worth. Reading the emitted signature is not a foreign hack bolted onto a clean design — it is the mechanism this file already runs on, applied to one more fact. That makes it safe and idiomatic, and it makes it no closer to a fix.

The layering test exempts it, for a reason that inverts. package sits in UNRANKED_PACKAGES in tests/test_layering.py, annotated “L7, which only ever runs after emission”. That is a sound reason not to constrain what may import it. It was read as putting L7 outside the discipline altogether, and the effect is that nothing requires the packaging layer to consume the plans that describe what it is packaging. Running last is precisely why it must agree with what ran before it.

Why every existing gate was blind to it. The byte-identity snapshot covers 505 files and the reproducibility harness covers 148 kernel digests across 8 materials; both operate on kernels, and neither compiles a wrapper. run_m9_regression.sh does have a wrapper syntax check, and it reports “skipped where ryml.hpp is unavailable” — which in a bare worktree is always, because ryml is a fetched dependency that exists only in a configured build tree. The framework’s strongest guarantees were structurally incapable of seeing the entire output of its last layer. spikes/codegen_wrapper_compile now compiles all 291 generated translation units against a real SFEM build; that is what found this, and it is the first thing that ever could have.

Contained, not fixed. The wrapper now asks what was actually emitted — whether the kernels declare a parameter of that name as an array — and spells the call to match. All 291 units compile, all eleven materials, nothing held out; 503 of the 505 snapshot files are byte-identical and the two that moved are exactly the two broken wrappers. But deriving the convention by reading generated text is still L7 reconstructing an L3 decision, one step later than before. It is a workaround with a green gate behind it, which is the most dangerous kind to leave unlabelled.

The call shape now comes from the element, and the scraping for it is gone. pipeline.driver._integration_case_for_material_element returns "isoparametric_mixed" when element.is_mixed_order, and that is the whole of what selects the mixed emitter — which keeps a vector field whole because MixedFieldLayout groups it, where the single-space model splits the same field into u0, u1, u2 in plans.residual_model._component_field_names. So the convention follows the element, and the element is something L7 already holds: mixed generations are handed an SfemCompatibleElement carrying the flag, non-mixed ones a plain element-name string that correctly carries nothing. _uses_mixed_field_arrays reads it, the 32-line text-scraping helper is deleted, and all 505 files stay byte-identical — the same output, now derived from the decision instead of from its printed consequence.

Note this was arrived at by elimination, not insight. Two cheaper rules were tried and measured first: keying on the wrapper’s builder path, which is wrong because the wrapper’s structure follows the material’s topology and the ABI follows the emitter’s; and keying on the field’s own shape, which cannot work because the field is identical in both cases — u with three components, confirmed by inspecting system.fields for both Kelvin–Voigt and Stokes.

package is now ranked L7 in LAYER_ORDER rather than sitting in UNRANKED_PACKAGES, so the import discipline applies to it and the annotation that read the exemption backwards is corrected.

The entry points the wrapper calls are now declared rather than recovered — and it turned out L7 authors them itself. The public *_2d_affine_mesh_soa family carrying the SFEM_CODEGEN_PUBLIC_C_ABI marker is written by _dispatch_function_lines in op_wrappers.py, from a parameter list it holds as data in group["params"]. So the wrapper was printing those signatures and then parsing them back out of its own output to learn their shape — which is the round trip that lost the array extent in the first place. _declared_dispatch_signatures records them as they are written, and the check now compares calls against what was declared. Byte-identical across all 505 files, and reintroducing the defect is still caught for both Stokes and poro.

The parse that remains is now total and partly self-checking. It used to drop any parameter it could not read a name from, which is precisely the failure that must be excluded rather than made unlikely: a signature one parameter short is still a signature, and the arity check downstream would then be comparing against a number the parse invented. It now raises instead. And because the dispatch entry points are both declared and recovered, the recovery is compared against a known answer — fifty to a hundred signatures per material, every generation.

That cross-check is weaker than it first looks, and the difference was established by injection rather than assumed. It covers the extraction: dropping a parameter while locating and splitting a declaration is caught. It does not cover _parse_c_parameter, because both sides go through it, so a defect there moves declared and recovered together and cancels — deleting every array extent is not caught. That half rests on the arity check and the compile spike. Claiming the parser was validated would have been wrong.

What is left is the ABI of the kernels the emitters author, which L7 genuinely does not see except as text: their parameter order and whether one takes the gradient metric. Publishing it from mesh_kernel_stream_plans and MixedFieldLayout is the remaining work, and it is the first piece of this that is large rather than fiddly. Kernels validate the matrix graph per element removed from every kernel — not yet re-established

Raised by Patrick, not found by this analysis. The generated Hessian assembly checks that the sparsity pattern contains every entry it needs while assembling. Each element's _scatter_bsr walks N_SHAPE × N_SHAPE candidate entries and tests each one with a three-condition branch, keeps a valid_block_graph flag, and calls std::fprintf(stderr, …) from inside an OpenMP parallel region on failure. The caller folds the status per element into invalid_matrix_graph and reduces it across threads with reduction(|:invalid_matrix_graph).

Graph validity is a property of the mesh and the sparsity pattern together — invariant across every element and across the whole assembly call. Establishing it once costs O(nnz); re-testing it inside the loop costs O(elements × N_SHAPE²), which is 100 branches per element for TET10 and far more for the higher-order hexes. Kernels must be correct, but preconditions belong to the caller: a kernel should be lean, and the priority inside an element loop is throughput.

Two facts shape the work. The check is fused into the sparsity search rather than sitting beside it — ks[j] is the search result and the branch validates it in the same pass — so removal keeps the search and drops the test, the flag and the I/O, rather than deleting a loop. And the CRS form carries the same pattern but is not currently emitted for any shipped material, so the real removal is smaller than the emitter source suggests.

Modified Mooney–Rivlin, worked as the concrete case, has 0 of 450: geometry_offset depends on the lane, grad_u_ref is gathered per lane, and every one of the 450 temporaries descends from one of the two.

Measured twice, on the material with the most of it, and it does not pay. Hoisting every genuinely invariant declaration above its lane loop and timing both builds at -O3: two-phase flow's tensor-product kernels, 84 declarations moved, no reproducible change — two apparent wins of +5% and +4% vanished on a repeat run, which is what a ±2% noise floor does to a single sample. Its simplex kernels, 224 declarations moved, median −1.25%, with 29 of 84 kernels worse than −2% against 4 better than +2%. Answers were bit-identical across all 36 kernels in both runs, so the analysis and the transformation are sound; they simply cost more than they save.

That is the register-pressure effect this entry predicted, now observed: moving scalar work out of a #pragma omp simd loop lengthens live ranges across it. LivenessState already models exactly this, which is the argument for a pass that consults it rather than one that hoists whatever it can.

Open, not closed, and deprioritised. Two of the three largest shares are still unmeasured — poro-elasticity and Stokes are Taylor–Hood on tetrahedra and want a TET10 grid the harness does not build. Given two negative results and an understood mechanism, the expected value is low; but the shares are the largest, so the item stays with its evidence attached. Anything that revisits it should hoist selectively under the liveness model rather than uniformly, and clear the ±2% floor on a machine that is not also full.

OP 14
The gate for changes that are meant to alter the output built — 54 kernels, 5 materials

Byte-identity has carried every step of this branch, and it is the strongest statement available while it holds. It is also unavailable for everything left: OP 10 hoists a check out of the kernels, OP 11 deletes dead declarations, OP 12 changes a scratch slot, OP 13 reconciles a name, and every loop-structure pass the IR is supposed to hold rewrites the text by design. For all of those, byte-identity is not the proof — it is the thing that must break.

tools/reproducibility.py is the gate that replaces it, asking the only question that survives an intended output change: given the same inputs, does the kernel still produce the same numbers? It generates each material, compiles the real entry points, drives every one it can bind over a Cartesian grid, and compares an l1/l2 digest per kernel against a committed baseline. --record rewrites that baseline, and the diff it produces is the reviewable statement of exactly which kernels moved.

Nothing in it knows any physics. The generated manifest lists every C ABI entry point with its full declaration, and the parameter names in those declarations are the ABI plans/streams.py defines — nelements, elements, g_jacobian_adjugate<i>, <role>_stride, <field>_direction, <field>_out. Binding a call is reading names, so a material added tomorrow is driven without touching the tool. That the boundary work of this session made those names a single definition is what makes this possible at all.

It carries a second check for free. The grid is affine, so a kernel pair differing only in geometry mode must agree — 24 such pairs, asserted rather than assumed. A digest alone would record a broken adjugate routing as the new correct answer; the parity check will not.

What it does not cover, stated rather than hidden. Packed variants want a mesh partition, matrix assembly wants a sparsity pattern, and the diagnostics entry points have no numerical output at all — each is skipped with its reason printed. Three materials are out of reach: poro-elasticity and Stokes are Taylor–Hood and want an element topology this grid does not build, and two-phase flow's per-form operators each define the same element-generic entry points, so they cannot be linked into one driver. That last one is a fact about the generated code worth its own look.

OP 13
Assembly plans named streams their kernels do not have described, not yet driven

Connecting the last four assembly plans found that two of them were describing a kernel that is not the one being generated. DIAAssemblyPlan.diagonal_offsets said "diagonal_offsets"; every DIA scatter reads a parameter called diag_offsets. COOAssemblyPlan said "rowidx" and "colidx"; the kernels write rows and cols. Nothing was wrong with the generated code — the plans had simply drifted, which they were free to do because no emitter read them. A plan nobody consults is free to be wrong about the thing it exists to define, and that is the strongest argument yet for connecting the rest.

The names could not simply be corrected: they are also the diagnostics index_policy, which is emitted into generated metadata and read by scripts/matrix_format_benchmark_report.py. So each plan keeps its descriptor and carries the C name alongside it — diagonal_offset_stream, row_stream, column_stream — and reconciling the two is a deliberate output change, batched with OP 11 and OP 12 rather than smuggled into a byte-identical step.

A third mismatch surfaced with them: COOAssemblyPlan has no reduction_policy at all. Its accumulation_policy is emit_triplets and its reduction_phase is non_hot_setup_phase, which describe the triplet scatter — but there are two COO kernels, and the other one locates its entry in a sorted graph and accumulates atomically in the hot loop. One plan, two kernels, and it describes one of them.

What is connected, and what is not. Each scatter now takes its stream names and reduction policy from its plan, and test_assembly_plans_name_the_kernels proves the plan is read rather than coincidentally matched, by renaming a stream and requiring the kernel to follow. What that does not yet give is a plan that drives the ABI: the same names appear as literals at roughly a hundred further sites — the mesh-operator signatures and the calls that pass the buffers in, fourteen for rowptr alone — so a rename reaches the scatter's parameters and not its callers, and the result would not compile. The docstrings on the CRS and BSR connections claimed otherwise and have been corrected.
