# The Stored-Tangent Apply

Partial assembly as a generated set-up and a library apply: the material tangent, pulled back to
the reference cell and weighted, is stored at every point of the rule the exact apply integrates
with, encoded, and applied many times without touching the state, the geometry or the material
again (`docs/compressed_partial_assembly`).

Plans: `plans/point_tangent.py` (the material), `plans/inexact_element.py` (the element and its
rule). Emitter: `emitters/inexact_codegen.py`. Library: `src/frontend/ops/inexact/`. Op surface:
`src/frontend/ops/sfem_Op.hpp`, generated by `package/op_wrappers.py`.

## Construction

The exact Hessian action is

```
(H h)_{i,p} = sum_q  S^q_{ikmn}  dh_k/dxi_m(xi_q)  dphi_p/dxi_n(xi_q)
S^q_{ikmn}  = w_q  A_{ijkl}(F(xi_q))  adj_{nj} adj_{ml} / det
```

`S^q` carries the weight, the geometry and the material. Store it, and the apply reads it and the
increment and nothing else: no geometry, no state, no material parameters. Nothing is projected,
so the stored apply is the exact one up to the encoding's rounding, on any cell — the tangent is
pulled back per point, so curved elements are stored as the exact apply integrates them.

What the rule can see decides what is stored (`plans/inexact_element.py`):

| element | stored per element | |
|---|---|---|
| TET4 | 1 point | |
| TET10 | 10 P2 moments `M^{ab} = sum_q lambda_a lambda_b S^q` | the reference derivatives of a P2 basis are linear, on any cell |
| HEX8, HEX27 (and their PROTEUS twins) | the points, folded | along a line in direction d, the m = n = d components multiply a polynomial of degree 2(p-1), so one point's value moves exactly to the others |

## Who owns what

| | where | |
|---|---|---|
| the material at one point | generated, `<unit>_<element>_inexact.hpp` | `point(parameters, gu_ref, gz_ref, adjugate, determinant, T)`: the unit's tangent, unweighted |
| the element | generated, `reference/inexact_<element>_q<n>.hpp` | stages (`stage_in`, `stage_out`, `setup_in`), weights, moment factors, fold tables, the node order the stages read |
| the contraction | generated, `reference/inexact_contract_d3.hpp` | one stored tangent against nine gradients, 45 (symmetric) or 81 numbers, masked forms for the fold |
| everything else | library, `src/frontend/ops/inexact/` | encodings, the point store, element matrices, the set-up loop, the traversals (atomic, packed two-pass), the Op state |
| the device stores | library, `src/frontend/ops/inexact/cuda/` | the same encodings in the GPU layouts and kernel shapes; `<unit>_<element>_inexact_store.cu` (generated) instantiates them per unit |

The element and contraction headers are material-independent and shared through the reference
family, so two materials on one element emit them byte for byte.

## The device

Under the CUDA target the same emitters print the device twins (`d3/<element>/cuda/*.cuh`,
`reference/cuda/`): the stages for one element per thread (no lane width, no lane loop), the
contraction with its masked forms, and for HEX27 the line's basis, which the point threads sweep
cooperatively. The device operator reaches each unit's stores through the factory its generated
source defines; its other methods are the host's.

The shapes are the ones measured on the H100 (`spikes/inexact_apply_compare/qp/RESULTS_QP.md`):
a thread per element on TET4, TET10 and HEX8 (block-local or atomic scatter, as measured per
store), a thread per point for HEX27's point store and a warp per element for its element
matrices. HEX8 folds; HEX27 does not on the device. The set-up runs a thread per element and point
in double and encodes in the host's order, so the device codes are the host's up to the rounding of
the arithmetic. `store: bsr` is the full difference form in SELL-32 with int32 columns.

## Symmetry

`symmetric` is asserted only when the flux's tangent difference expands to exactly zero. An
energy's tangent is a Hessian and symmetric (45 numbers); a residual's is a Jacobian and generally
not (Kelvin–Voigt viscosity: 81). The symmetry is `S[i,k,m,n] == S[k,i,n,m]`: `(i,n)` swaps with
`(k,m)`, which only a comparison against a directly integrated action can catch
(`tests/test_inexact_point_tangent.py`). An unsymmetric tangent refuses CG
(`UnconstrainedStep`) and stores both off-diagonal blocks of its element matrices.

## Rate-dependent materials

The previous state is data: its gradient enters the point function as `gz_ref` and is never
differentiated against. A material mixing an energy with a residual publishes from the unit
carrying its whole residual (`plans/residual_structure.publishes_inexact_apply`), and the stored
tangent is that unit's.

## The Op contract

```cpp
bool inexact_supported() const;          // every domain's element has a unit
bool tangent_is_symmetric() const;
void set_inexact_options(const InexactOptions &);   // before the next update
int  inexact_update(const real_t *x);    // evaluate and encode at x
int  inexact_apply(const real_t *h, real_t *out);   // adds, takes no state
```

`inexact_update` is explicit: a Newton step stores once and applies for every Krylov iteration.
`inexact_apply` adds the time scheme's inertia term, as the exact apply does. Applying before
updating is an error.

## Options

`solver.linear.format: INEXACT` with `solver.linear.inexact: {store, encoding, fold, traversal}`:
`points` (f64, f32, f16, i8md) or `element_matrix` (f64, f32, f16, i8pair); `fold: auto|on|off`;
`traversal: auto|packed|atomic` (the device chooses its own: `auto` only). int8 with one scale per element is not offered: it is not a
usable Newton operator.

## Opt-in

Off by default. `inexact_apply=True` on the material, or `--inexact-apply` /
`--no-inexact-apply` on the generator. A material that does not ask generates nothing and
overrides nothing, so `Op`'s refusing defaults stand.
